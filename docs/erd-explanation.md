# شرح مخطط ERD لمنصة «استجابة» (الإصدار 1.1)
شرح تفصيلي لجداول قاعدة البيانات المنطقية وعلاقاتها، مستند إلى وثيقة SRS الإصدار 1.1. الملف المرافق: `erd_v1.1.dbml`.

## ما الذي تغيّر عن النسخة السابقة؟

| # | التعديل | السبب |
| :--- | :--- | :--- |
| 1 | `report_status` أصبحت 7 حالات: `received`, `under_review`, `assigned`, `en_route`, `on_site`, `mission_completed`, `closed` | توحيدها مع القسم 7 من SRS 1.1 |
| 2 | `mission_status` قيمها تطابق حالات البلاغ (`mission_completed` بدل `completed`) مع إضافة `cancelled` | منع التعارض بين الجدولين، ودعم إعادة الإسناد |
| 3 | حُذفت المراجع `BR-001` إلى `BR-010`، واستُبدلت بمتطلبات FR/NFR الفعلية | هذه المراجع غير موجودة في SRS |
| 4 | حُذف ذكر Whisper، وصار الوصف «مكوّن تحويل الصوت إلى نص» | إبقاء الوصف مجرداً حسب ملاحظات المشرف |
| 5 | أُضيف إلى `users`: `last_known_location`, `location_updated_at`, `location_consent` | FR-012 و FR-027 يحتاجان موقع المستخدم |
| 6 | أُضيف `audit_logs.reason` | FR-037 يوجب سبباً عند كشف الهوية |
| 7 | جدول جديد `system_settings` | FR-036 |
| 8 | جدول جديد `refresh_tokens` | FR-003: إبطال الجلسة عند الخروج |
| 9 | أُضيف `ai_extractions.is_anonymous` | المواطن يختارها قبل التأكيد (FR-009) |
| 10 | جدول جديد `simulated_integration_logs` | FR-039 |
| 11 | أُضيف `assignments.cancelled_at` | إعادة الإسناد |
| 12 | أُضيفت إلى `users` علاقة `field_unit_id` ملاحظة بأنه إلزامي لدور ممثل الوحدة فقط | قاعدة تُنفَّذ في التطبيق |

## 1. كيف تقرأ الـ ERD؟
* **الجدول (Table):** كيان من النظام، مثل المستخدم أو البلاغ.
* **`pk`:** المفتاح الأساسي، قيمة فريدة تعرّف كل صف.
* **`ref: >`:** مفتاح أجنبي بعلاقة **many-to-one**. و`ref: -` علاقة **one-to-one**.
* **`not null`:** الحقل إلزامي. **`unique`:** القيمة لا تتكرر.
* **`Enum`:** قائمة قيم محددة مسبقاً، مثل حالات البلاغ.

## 2. الحسابات والصلاحيات (FR-001 إلى FR-004)

### `users`
| الحقل | المعنى |
| :--- | :--- |
| `id` | معرف `UUID`. |
| `role_id` | دور المستخدم. |
| `field_unit_id` | الوحدة الميدانية. إلزامي لدور ممثل الوحدة، وفارغ للباقين (يُتحقق منه في التطبيق). |
| `full_name`, `email`, `phone` | بيانات الحساب. البريد والهاتف `unique` لمنع الحسابات المكررة (FR-001). |
| `password_hash` | كلمة المرور مشفّرة بـ hash. |
| `is_active` | تعطيل الحساب دون حذفه (FR-034). |
| `last_known_location` | آخر موقع معروف، لتحديد من يصله التنبيه الجغرافي (FR-012، FR-027). |
| `location_updated_at` | وقت آخر تحديث للموقع. |
| `location_consent` | إذن المستخدم بمشاركة موقعه. لا يصله تنبيه جغرافي إلا إذا كان `true`. |

> التزاماً بـ NFR-012، لا تُجمع بيانات شخصية غير ضرورية.

### `roles`
أربعة صفوف: `Citizen`, `Dispatcher`, `Field Unit Representative`, `System Administrator`.

### `permissions` و`role_permissions`
لكل صلاحية `code` مثل `report.assign` و`report.close` و`identity.reveal`. الجدول الوسيط يمثل **many-to-many** بمفتاح أساسي مركّب `(role_id, permission_id)`. يتحقق الـ Backend من هذه الجداول لتطبيق RBAC (NFR-007)، ويستطيع المدير تعديل الصلاحيات دون تغيير الكود (FR-004).

### `refresh_tokens` (جديد)
يخزن hash لرمز التجديد، وتاريخ انتهائه، و`revoked_at` الذي يُملأ عند تسجيل الخروج. بهذا لا يمكن استخدام الرمز بعد الخروج (FR-003، NFR-006).

## 3. البلاغات (قلب النظام)

### `report_types`
* `category`: التصنيف الرئيسي (FR-008).
* `name`: النوع الدقيق. يُضاف في بيانات البداية (seed) نوع جاهز اسمه «SOS عام»، لأن بلاغ SOS لا يختار نوعاً و`report_type_id` إلزامي.
* `responsible_authority`: الجهة المقترحة. التكامل معها محاكاة (FR-039).
* قيد `unique` على `(category, name)`.

### `reports`
| الحقل | الشرح |
| :--- | :--- |
| `reporter_id` | المبلّغ. مملوء دائماً حتى لو كان البلاغ مجهولاً، ليتتبع بلاغه (FR-010). |
| `report_type_id` | إلزامي. |
| `source` | `sos` أو `manual` أو `ai_bot`. |
| `is_anonymous` | إن كانت `true` تُحجب الهوية عن المشغل والوحدة ويظهر «مبلّغ مجهول» (FR-009). مسموحة للبلاغ اليدوي وبلاغ المساعد الذكي فقط. |
| `location`, `location_text` | الموقع الجغرافي ووصفه النصي. الموقع قد يكون فارغاً إن تعذر تحديده (FR-006). |
| `severity` | منخفضة، متوسطة، عالية، حرجة. |
| `priority_score` | يساعد في الترتيب فقط ولا يلغي قرار المشغل (FR-022). |
| `current_status` | إحدى الحالات السبع (القسم 7). |
| `administrative_area` | للتصفية (FR-020). |
| `close_reason`, `closed_by`, `closed_at` | بيانات الإغلاق. السبب إلزامي (FR-028). |

الفهارس على `current_status` و`created_at` و`reporter_id` تسرّع التصفية وتحديث الخريطة خلال ثانيتين (NFR-002).

### `report_timeline`
سجل لكل تغيير في الحالة: الحالة الجديدة، ومن غيّرها، وملاحظة، والوقت. يغذي تتبع المواطن (FR-010) وبطاقة التفاصيل (FR-023) ويحقق متطلب السجل الزمني في القسم 7. `changed_by` فارغ عندما يكون التغيير من النظام (الحالة الأولى). الفرق بينه وبين `reports.current_status`: الأخيرة هي الحالة الآن للعرض السريع، والجدول هو التاريخ الكامل.

### `report_attachments`
صور أو فيديو أو ملاحظة صوتية قصيرة للبلاغ **اليدوي** (FR-007). يخزن الرابط والنوع والحجم، والملف نفسه في مخزن خارجي. التسجيلات الصوتية لبوت الإبلاغ الذكي لا تُخزَّن هنا ولا في أي مكان (FR-018، NFR-015).

## 4. بوت الإبلاغ الذكي (FR-013 إلى FR-018)

### `ai_extractions`
مسودة البلاغ قبل أن يصبح بلاغاً حقيقياً:
* `input_mode`: نص أو صوت.
* `input_text`: النص الحر، أو نص الصوت بعد تحويله بمكوّن تحويل الصوت إلى نص. لا يوجد عمود للملف الصوتي لأنه يُحذف بعد التحويل.
* `extracted_*`: ما استخرجه مكوّن الذكاء الاصطناعي: النوع والخطورة والموقع والوصف (FR-015).
* `is_anonymous`: اختيار المواطن قبل التأكيد، وينتقل إلى `reports` عند الإنشاء.
* `status`: `pending_review` ثم `edited` ثم `confirmed` أو `cancelled` (FR-016).
* `report_id`: **one-to-one** مع البلاغ، ولا يُملأ إلا بعد التأكيد الصريح (FR-017).
* `user_id`: رابط داخلي فقط. لا تُرسل الهوية لمكوّن الذكاء الاصطناعي (FR-018، NFR-014).

## 5. الدردشة (FR-025)

### `chat_messages`
البلاغ، والمرسل، والنص، ووقت الإرسال. المحادثة مرتبطة بالبلاغ. إذا كان البلاغ مجهولاً يعرض الـ API للمشغل «مبلّغ مجهول» دون تغيير في الجدول.

## 6. الوحدات الميدانية والإسناد

### `field_units`
الاسم، والنوع (شرطة، دفاع مدني، إسعاف، مرور)، والتوفر (`available`, `busy`, `offline`)، والموقع لعرضه على الخريطة (FR-021).

### `assignments`
* `assigned_by`: المشغل الذي اتخذ القرار (FR-026).
* `mission_status`: `assigned` ثم `en_route` ثم `on_site` ثم `mission_completed`، أو `cancelled` عند إعادة الإسناد (FR-032).
* `en_route_at`, `on_site_at`, `completed_at`, `cancelled_at`: وقت كل مرحلة.
* الوحدة تستعلم من هذا الجدول فقط لتعرف بلاغاتها (FR-031).
* قاعدة: إسناد واحد غير ملغى لكل بلاغ في أي لحظة. تُنفَّذ بفهرس فريد جزئي (partial unique index) في PostgreSQL، وهو غير ممكن في DBML.

**اتساق الحالتين:** عند تحديث الوحدة لحالة المهمة، يُحدَّث `assignments.mission_status` و`reports.current_status` وسجل `report_timeline` في **transaction واحدة**.

### `field_actions`
تقرير الإجراء الميداني (FR-033)، مرتبط بالإسناد لأنه يخص مهمة وحدة معينة.

### `simulated_integration_logs` (جديد)
سجل بسيط لطبقة المحاكاة (FR-039): الجهة، والطلب المرسل، والرد التجريبي. الطبقة نفسها لا تحتاج جداول أخرى.

---

## 7. التنبيهات والإشعارات

### `geographic_alerts`
العنوان ووصف الخطر ومركز الدائرة `center` ونصف القطر `radius_m` بالمتر (FR-027). الجدول غير مذكور صراحة في كيانات SRS وأُضيف لدعم هذا المتطلب.

### `notifications`
* `type`: `status_update` أو `assignment` أو `closure` أو `geographic_alert`.
* `report_id` و`alert_id`: اختياريان، ويُملأ أحدهما حسب النوع.
* `is_read`: حالة القراءة.
* عند التنبيه الجغرافي يُنشأ صف لكل مستخدم يقع `last_known_location` له داخل الدائرة وقد منح `location_consent`.
* إشعار المبلّغ (FR-038) يصل حتى لو كان البلاغ مجهولاً.

## 8. الإدارة والتدقيق

### `audit_logs`
* `action`: مثل `report.edit` و`report.close` و`report.assign` و`identity.reveal` و`user.disable`.
* `entity_type` و`entity_id`: الكيان الذي حدث عليه الفعل.
* `old_value` و`new_value`: `jsonb` للحالة قبل التعديل وبعده.
* `reason`: إلزامي عند `identity.reveal` (FR-037)، ويُتحقق منه في التطبيق.
* `ip_address`: عنوان الجهاز.
* يغطي FR-024 وFR-035 وNFR-010. كل كشف لهوية مبلّغ مجهول يُسجَّل هنا (من كشف، أي بلاغ، متى، لماذا).

### `system_settings` (جديد)
مفتاح وقيمة لإعدادات عامة (FR-036)، مثل مهلة إلغاء SOS (5 ثوانٍ افتراضياً). يُسجَّل كل تعديل في `audit_logs`.

## 9. العلاقات (Cardinality)

| العلاقة | النوع |
| :--- | :--- |
| `roles` ← `users` | واحد إلى متعدد |
| `roles` ↔ `permissions` | متعدد إلى متعدد عبر `role_permissions` |
| `field_units` ← `users` | واحد إلى متعدد |
| `users` ← `refresh_tokens` | واحد إلى متعدد |
| `users` ← `reports` | مواطن واحد له عدة بلاغات |
| `report_types` ← `reports` | نوع واحد لعدة بلاغات |
| `reports` ← `report_timeline` / `report_attachments` / `chat_messages` | بلاغ واحد له عدة سجلات |
| `reports` ↔ `ai_extractions` | واحد إلى واحد (اختياري من جهة البلاغ) |
| `reports` ← `assignments` | بلاغ قد يُسند أكثر من مرة، وإسناد واحد فعّال فقط |
| `field_units` ← `assignments` | وحدة واحدة لها عدة مهام |
| `assignments` ← `field_actions` | إسناد واحد له عدة تقارير |
| `assignments` ← `simulated_integration_logs` | إسناد واحد له عدة سجلات محاكاة |
| `users` ← `notifications` | مستخدم واحد له عدة إشعارات |
| `geographic_alerts` ← `notifications` | تنبيه واحد يولّد عدة إشعارات |
| `users` ← `audit_logs` | مستخدم واحد له عدة سجلات |

## 10. سيناريو كامل: بلاغ عبر البوت الصوتي

1. المواطن يسجل رسالة صوتية، فيُنشأ صف في `ai_extractions` (`input_mode = voice`) ويُحذف الملف الصوتي بعد تحويله إلى نص.
2. مكوّن الذكاء الاصطناعي يملأ الحقول `extracted_*` فتصبح الحالة `pending_review`.
3. المواطن يراجع ويعدّل فتصبح `edited`، ويختار إخفاء الهوية إن أراد، ثم يؤكد فتصبح `confirmed`.
4. عند التأكيد يُنشأ صف في `reports` (`source = ai_bot`, `current_status = received`) ويُربط بالمسودة، ويُضاف أول سجل في `report_timeline`.
5. المشغل يفتح البلاغ فتصبح الحالة `under_review`. ثم يسنده لوحدة فينشأ صف في `assignments` وتصبح الحالة `assigned`، ويُنشأ إشعار للمبلّغ.
6. ممثل الوحدة يحدّث المهمة إلى `en_route` ثم `on_site`، فتتحدث `assignments` و`reports.current_status` و`report_timeline` معاً، ويصل المواطن إشعار.
7. الوحدة ترفع تقريرها في `field_actions`، وتصبح الحالة `mission_completed`.
8. المشغل يغلق البلاغ مع سبب إلزامي فتصبح `closed`، ويُسجَّل ذلك في `audit_logs` ويُشعَر المواطن.

## 11. افتراضات وملاحظات

1. **الإخفاء ليس في قاعدة البيانات:** الجدول يحتفظ بالهوية الحقيقية دائماً. الإخفاء يتم في طبقة الـ API والصلاحيات، ويجب اختباره بتست آلي: لا ترجع نقاط نهاية المشغل والوحدة الميدانية أي بيانات هوية للبلاغ المجهول.
2. **قواعد تُنفَّذ في التطبيق** (لا يعبّر عنها DBML): `field_unit_id` إلزامي لدور ممثل الوحدة، و`close_reason` إلزامي عند `closed`، و`audit_logs.reason` إلزامي عند `identity.reveal`، و`is_anonymous` غير مسموحة لبلاغ SOS.
3. **`priority_score`:** خوارزمية حسابه غير محددة في SRS، والنوع `numeric(6,2)` اقتراح.
4. **`geographic_alerts` و`system_settings` و`refresh_tokens` و`simulated_integration_logs`:** أُضيفت لدعم FR-027 وFR-036 وFR-003 وFR-039، وهي غير مذكورة كأسماء كيانات في SRS.
5. **التقنيات:** استُخدمت صيغ PostgreSQL/PostGIS (`geography`, `jsonb`, `inet`) لأن DBML يحتاج أنواعاً فعلية. ويبقى اختيار التقنية النهائي في وثيقة التصميم.
6. **نوع المخطط:** ERD منطقي وليس الفيزيائي النهائي.

## 2. Backend (`apps/api`)

### 2.1 Migrations vs DBML (no new migration)
The S0 migrations for `roles`, `permissions`, `role_permissions`, `users`, `refresh_tokens` and `audit_logs` are checked against the DBML by `pnpm schema:drift` (green in S0). S1 adds **no table, column or enum**. Constraints that follow from this:

### 2.3 JWT access tokens (NFR-006)
- `php-open-source-saver/jwt-auth`. It is named in the `apps/api/CLAUDE.md` stack but **is not installed** (`composer.json`/lock have no trace of it), so it is a new dependency for your approval (Q3). It is pinned to the newest release that supports Laravel 13, and the exact version is checked on Packagist at install time. The `api` guard uses driver `jwt` and becomes the default guard.
- Access TTL **15 min** (`JWT_TTL=15`), HS256 with `JWT_SECRET` from `.env`, refresh TTL **30 d**. All are configurable in `config/jwt.php` and `config/auth-tokens.php` and read only via `config()`.
- **Every authenticated request:** a valid signature, not expired, `jti` not on the denylist, user exists and `is_active = true`. Otherwise 401 `unauthenticated`. The contract's `Unauthorized` response explicitly covers deactivated accounts.

### 2.4 Refresh tokens: rotation and reuse detection
- The refresh token is opaque: 64 random bytes, base64url. Only `hash('sha256', token)` is stored in `token_hash`. A deterministic hash is needed for the lookup, and the token has full entropy, so a slow hash adds nothing.
- **Rotation:** `RefreshTokenAction` runs in a transaction with `lockForUpdate` on the row. It runs these checks in order:
  1. **Not found:** 401.
  2. **Expired:** 401.
  3. **Revoked:**
     - If the `rotated:{hash}` cache marker exists, this is **reuse**. Revoke every unrevoked refresh token of that user and return 401. A redacted log line is written (no token, no user PII).
     - Otherwise (it was revoked by logout or a password change), return a plain 401.
  4. **User inactive:** 401.
  5. **Otherwise:** set `revoked_at` on the token, write the `rotated:{hash}` marker (TTL = the token's remaining lifetime), insert the new row, and return a new `TokenPair`.
- The cache marker is needed because the DBML has no column for the revocation reason. If the cache is lost, reuse becomes a plain 401 (the presented token still fails; only the family revocation is skipped).
- **Known effects (documented risks, §8):** a duplicated browser tab copies `sessionStorage`. If both tabs refresh, reuse detection logs out both. On mobile, a refresh whose response is lost has the same effect. Both outcomes are safe.

### 2.5 Logout (FR-003)
- `LogoutAction`: sets `revoked_at` on the supplied refresh token **only if it belongs to the caller**. A token that is unknown, belongs to someone else, or is already revoked still returns 204, so nothing is revealed and logout is idempotent.
- The current access token is added to the **`jti` denylist** with TTL `exp - now` (the jwt-auth blacklist on the app cache store). A request with that token then gets 401 immediately. This closes I-07 / D-05.

### 2.6 Login and lockout (FR-002, NFR-011, H4)
- **Order:**
  1. Rate limit (10/min/IP; this layer returns 429 `rate_limited`).
  2. Lockout check (returns 429 `account_locked` + `Retry-After`).
  3. Credential check. A **dummy Argon2id verify runs when the email is unknown**, so timing is equalized. A failure returns 401 `invalid_credentials`.
  4. `is_active` check, **after** a correct password: 403 `account_deactivated`.
  5. Issue a token pair.
- **Lockout:** two independent counters in the cache:
  - `login:fail:acct:{sha256(lower(email))}` is keyed on the **submitted email string, whether or not the account exists**. A locked state therefore never proves that an email is registered.
  - `login:fail:ip:{ip}`.
- 5 failures inside a rolling 15-min window lock that key for 15 min (both values configurable). While locked, even a correct password gets 429 and does not extend the lock.
- A success clears the account counter but **not** the IP counter, so an attacker cannot reset it with their own account.
- **Audit (H4):** one `auth.lockout` row each time a lock starts:
  - `entity_type = 'user'`, `entity_id` = the user id if the account exists, otherwise `entity_type = 'login_identifier'` with a null id.
  - `new_value = {scope: account|ip, locked_until}` and `ip_address`.
  - Never the email, password or phone.

### 2.7 Registration (FR-001)
- Citizen role only, resolved server-side by the seeded name `Citizen`. The body cannot carry a role (`additionalProperties: false`, so 422).
- Validation:
  - `full_name` 1–150.
  - `email`: RFC email ≤255, lowercased.
  - `phone`: required, ≤30, plus the pattern from §9 gap 6 once approved.
  - `password`: ≥8 (D-06).
- **Duplicates:**
  - 409 `email_taken` or `phone_taken` (email is checked first).
  - Backed by catching the unique-index violation as well, because of races.
- Response: 201 `CurrentUser`, **no tokens**. The client then calls `login`.

## 3. `packages/api-client`: audit and S1 changes

**What exists (S0):**
- `createApiClient(options)`:
  - Bearer from `getAccessToken`.
  - `Accept-Language` from `getLanguage`.
  - A single-flight refresh with one queued retry for each 401.
  - `onSessionExpired`.
  - `withIdempotencyKey`.
- Upload progress through Axios `onUploadProgress` (type re-exported as `UploadProgressEvent`).
- `ApiError {status, code, message, request_id, errors?, retryAfterSeconds?}` and `toApiError`.
- Contract type helpers.
- 17 tests.

**Gaps found (all are S1-relevant):**
1. **Public auth calls trigger a refresh.** A 401 from `login` (`invalid_credentials`, once §9 is approved) or from `logout` currently enters the refresh path. It calls `refresh()` and then `onSessionExpired`, which is a spurious "session expired" on a wrong password.
   - **Fix:** attempt a refresh only when the failed request **carried a Bearer token**, and never for `refreshPath`. Add an optional `noRefreshPaths` (default `['/auth/login', '/auth/register', '/auth/refresh', '/auth/logout']`).
2. **204 responses are typed `never`.** `SuccessBody` only maps 200/201/202, so `await request('post','/auth/logout')` and `PUT /me/location-consent` type as `Promise<never>`, and code after them is unreachable to TypeScript.
   - **Fix:** map 204 (and 202 with no body) to `void`. Add a type test.
3. **A refresh that fails on the network logs the user out.** A `network_error` (status 0) during refresh currently fires `onSessionExpired`.
   - **Fix:** only fire it when the refresh failed with 401/403. On a network error, reject the queued requests with `network_error` and keep the session.
4. **No helper to tell error kinds apart.** Add `isApiError(e)` and an exported `ApiErrorCode` string-literal union of the contract and S1 codes (incl. `network_error`, `unknown_error`), so Track B and web map codes to i18n without string typos.

**Stable exports Track B can rely on after Checkpoint 1:**
- `createApiClient`, `ApiClient`, `ApiClientOptions` (adds the optional `noRefreshPaths`; existing fields unchanged), `Language`, `RequestOptions`.
- `ApiError` (fields unchanged), `toApiError`, `isApiError`, `ApiErrorCode`.
- `UploadProgressEvent`, `HttpMethod`, `MethodsOf`, `Operation`, `PathParams`, `QueryParams`, `RequestBody`, `SuccessBody` (now `void` for 204).

There are no breaking changes to S0 signatures.

**Behaviour contract for Track B:**
- `refresh()` must store the new access token (so `getAccessToken()` returns it) **before** resolving. The retry re-reads it.
- `refresh()` must throw an `ApiError` (status 401) when the server rejects the token.

- **`createWebAuthSession({ api, appRole })`:** a factory that both apps use, so the token rules live in one place. It holds:
  - **Zustand store** `{status: 'unknown'|'signedOut'|'signedIn', user: {id, role, permissions} | null}`. This is the *session* state only. It never holds the profile fields (those stay in TanStack Query `['me']`) or tokens.

    1. Call `POST /auth/login`.
    2. Call `GET /me`.
    3. If `role !== appRole`: call `logout` (revokes the refresh token), clear everything, and throw `wrong_app_role`.
    4. Otherwise set `signedIn`.
  - **`refresh()`** is passed to `createApiClient`. It rotates the token and stores the new pair.
  - **`logout()`:** `POST /auth/logout`, then clear memory, storage and the query cache, whatever the result.
  - **Bootstrap on page load:** if a refresh token is in `sessionStorage`, call `refresh()`, then `GET /me` and the role check; otherwise `signedOut`.
- The apps' `src/lib/api.ts` becomes a thin wire-up of `createApiClient` + `createWebAuthSession`.

## 8. Risks, open questions, Definition of Done

### Risks
- **R1, reuse detection vs duplicated tabs and lost responses (§2.4).** Both are safe (logout). It is documented in the web UX: "signed out for security, sign in again".
- **R2, lockout as a DoS lever.** Anyone can lock a known email for 15 min. Accepted by the approved rule; per-IP plus per-account keeps it bounded, and the audit row makes it visible.
- **R3, registration enumeration.** `email_taken` / `phone_taken` reveal registered identifiers. This is inherent in "prevent duplicates with a clear message" (FR-001) without email verification, and mitigated by 5/hour/IP.
- **R4, `/me/password` at 120/min.** A stolen access token could brute-force the current password. Mitigations: the 15-min access TTL, and optionally applying the login lockout counters to wrong current passwords (Q4).
- **R5, `x-proposed` operations have no SRS FR.** Tests for profile/password carry `D-38` groups plus the nearest NFR/FR. The traceability script only checks SRS IDs, so this is fine.
- **R6, Checkpoint 1 before the backend exists.** Track B codes against Prism. Prism will not return the new 401/403/409 codes until §9 is merged, so §9 must land in Checkpoint 1.

### Open questions
- **Q1 (answered):** include `updateMyLocation` in S1, backend only.
- **Q2:** On consent revoke, clear `location_updated_at` as well as `last_known_location` (D-15 names only the location)? **Recommendation:** yes. A timestamp without a location is meaningless, and `CurrentUser` exposes it.
- **Q3 (answered, all approved):** the new dependencies:

### Contract notes for Track B (S1-mobile)
1. **Registration returns `CurrentUser` with no tokens.** Call `login` next.
2. **Login errors** (after §9):
   - 401 `invalid_credentials`;
   - 403 `account_deactivated`;
   - 429 `account_locked` (lockout) or `rate_limited` (10/min), both with `Retry-After`.
   - Show minutes from `ApiError.retryAfterSeconds`.
3. **Refresh:**
   - Rotation on every call. Always store the newly returned refresh token in `expo-secure-store` *before* using the access token.
   - Never retry a refresh call automatically: replaying a rotated token triggers reuse detection, and the server then revokes **all** of the user's sessions.
   - 401 means signed out.
4. **Logout:** send the refresh token. The access token is dead immediately (denylist). 204 even if the token is unknown.
5. **Role mismatch:** "reject and log out" must call `POST /auth/logout` (server-side revocation), not just delete local tokens.
6. **Password change:** the response is a new `TokenPair`, so replace both tokens. Other devices are signed out on their next refresh.
7. **Location:**
   - Revoking consent clears the stored location server-side.
   - `PUT /me/location` is real from Checkpoint 2. It returns 409 `location_consent_required` without consent, and 429 above 10/min (not in the contract yet, Q8).
   - Send it only in the foreground, every 60 s.
8. **Phone format:** E.164 (approved), e.g. `+963933123456`. Validate client-side with `^\+[1-9][0-9]{7,14}$`.
9. **Deactivation:** an account deactivated mid-session gets 401 `unauthenticated` on the next call, and the refresh also returns 401.
10. **api-client:**
    - Use the Checkpoint 1 version: login 401s no longer trigger refresh, and 204 calls are typed `void`.
    - Use `isApiError` / `ApiErrorCode` for mapping.
    - New strings live in the i18n `errors` namespace. Do not duplicate them in mobile namespaces.
